# 应用更新机制调研

调研日期：2026-11-03。范围：macOS 应用本身的检查更新、提醒、下载和安装；公开安装包以 GitHub Releases 为唯一下载渠道。产品交互已确认，应用端与发布脚本已实现；验证和上线条件见文末。

## 成熟应用的实际做法

### Rectangle：常驻应用的低打扰提醒

Rectangle 使用 Sparkle，配置每 172800 秒（48 小时）检查一次。它保留手动检查入口，并把自动检查开关同步给更新器。[Info.plist](https://github.com/rxhanson/Rectangle/blob/main/Rectangle/Info.plist#L43-L48)、[AppDelegate](https://github.com/rxhanson/Rectangle/blob/main/Rectangle/AppDelegate.swift#L131-L133)

最值得借鉴的是提醒方式：自动检查发现更新、且更新无需立即取得焦点时，不直接弹窗口，而是记录待更新状态，把菜单入口改成“Update Available…”。用户主动检查时，再进入 Sparkle 更新流程；会话结束后恢复“Check for Updates…”。这是源代码中可直接确认的行为，未实机观察其窗口外观。[提醒回调](https://github.com/rxhanson/Rectangle/blob/main/Rectangle/AppDelegate.swift#L633-L651)、[手动入口](https://github.com/rxhanson/Rectangle/blob/main/Rectangle/AppDelegate.swift#L271-L273)

其 README 提供官网和 GitHub Releases 下载入口，但应用内更新清单放在网站。它说明了“下载渠道”和“更新元数据地址”可以独立选择，不能据此声称其所有更新流量只经过 GitHub。[官方 README](https://github.com/rxhanson/Rectangle#installation)

### CotEditor：GitHub 安装包也能应用内升级

CotEditor 官方说明：非 App Store 版使用 Sparkle 提醒并更新，App Store 版交由系统管理；非商店版本经过 Apple 公证。[官方下载说明](https://coteditor.com/archives)

其公开 appcast 包含构建号、展示版本、最低 macOS 版本、多语言更新说明链接和下载签名；安装包地址直接指向 GitHub Releases 的 DMG。同一份清单保留不同 macOS 版本可用的发布项。因此，只在 GitHub 发布安装包，并不妨碍实现原生一键更新。[官方 appcast 源文件](https://github.com/coteditor/coteditor.github.io/blob/main/appcast.xml)

### IINA：稳定版与测试版分开

IINA 官方下载页允许用户在设置中开启“Receive beta updates”；源代码根据该偏好选择稳定或 beta 更新清单。它还把 nightly 单列为开发构建，不与普通稳定版混在一起。[官方下载页](https://blog.iina.io/download/)、[更新清单选择逻辑](https://github.com/iina/iina/blob/develop/iina/AppDelegate.swift#L176-L180)

这一点适合未来需要测试渠道时借鉴；当前若只有正式版本，没有必要先增加渠道选择界面。

## 已确定的产品交互

2026-11-03 用户明确要求克制设计：静默检查，发现新版本只在现有版本号区域显示红点，由用户决定是否更新。该决定替代此前关于菜单提示、首次询问和额外检查入口的建议。

| 场景 | 确定行为 |
| --- | --- |
| 平时常驻 | 静默检查更新，没有更新时保持原样。 |
| 发现可用新版 | 仅在工作台现有版本号区域显示一个红点，不增加“有新版本”标签、不弹窗、不发系统通知、不展开小岛。 |
| 用户点击版本区域 | 主动进入更新界面，查看目标版本和简洁更新说明，再决定是否下载安装。 |
| 用户未选择更新 | 继续正常使用，不自动下载、安装或重启。 |
| 后台检查失败 | 安静处理，后续重试，不把网络错误当成“已是最新”。 |
| 用户主动更新失败 | 在已打开的更新界面内提供必要反馈和重试操作。 |

第一版只保留版本区域这一入口，不增加菜单更新提示、首次自动检查询问或独立更新设置。检查周期暂建议 24 小时，属于实现参数，不增加配置界面。关闭更新界面保留红点；选择跳过版本清除，后续静默检查遵循框架的跳过记录；成功升级后清除旧版缓存。

安装仍由用户决定时机。灵宠岛当前任务列表为内存状态，不能承诺更新后恢复；必要的重启影响说明放在用户主动进入的更新流程内。

灵宠岛的安装退出还必须沿用现有退出流程：保持唤醒恢复失败时，应用可能取消退出。更新流程应允许这次安装延后，不能绕过退出检查或强制杀死应用。本段依据主线程对本仓库 `PRIVACY.md` 和 `applicationShouldTerminate` 的核查，框架接入时仍需验证该路径。

## 技术建议：Sparkle 2 + GitHub Releases

推荐使用 Sparkle 负责版本比较、下载、验签、安装及重新启动，灵宠岛负责入口和提醒策略。只检查新版本并打开发布页是成本较低的备选，但用户仍要手动拖拽安装；自行编写替换运行中应用的更新器会增加安装、权限与失败恢复的维护成本。[Sparkle 官方能力说明](https://github.com/sparkle-project/Sparkle)

发布设计建议如下（方案尚未端到端验证）：

1. 保留现有 DMG 和 SHA256SUMS，新增 Sparkle `appcast.xml` 更新清单附件。DMG 本身可同时供首次下载和 Sparkle 更新使用。
2. 应用固定读取 `https://github.com/LJjayyy/LingChongDao/releases/latest/download/appcast.xml`。GitHub 官方支持 latest Release 的固定文件名附件入口；该地址目前只是计划地址，不表示文件已发布。无需额外服务器或 GitHub API token。
3. 清单里的 DMG 地址指向具体版本的 Release，不能使用会随 latest 变化的包地址；包括递增构建号、展示版本、最低系统要求及 EdDSA 签名。清单保留必要历史项，便于将来提高系统要求后仍为旧系统找到兼容版本。
4. CI 构建验证后，完成包签名、生成清单，再上传到草稿 Release；确认附件齐全后发布并标记 latest。正式通道不能把预发布或无清单的 Release 标成 latest。
5. 第一版使用完整包更新，后续有体积需求再引入差分更新。更新说明优先嵌入清单，减少额外地址维护。

上述固定入口是结合 GitHub 与 Sparkle 官方能力提出的设计，仍需验证重定向、缓存、清单解析与完整升级链路。[GitHub 附件链接规则](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)、[Sparkle 发布指南](https://sparkle-project.org/documentation/publishing/)

实际采用 Sparkle 的纯信息探测 `checkForUpdateInformation()`，成功后间隔 24 小时、失败后约 1 小时再试；关闭框架自带定时检查。后台探测仅驱动版本号红点，点击后才调用标准更新窗口，避免 Gentle Reminders 的启动附近弹窗分支。自动下载安装、检查权限询问和系统画像上传均关闭。[提醒接口](https://sparkle-project.org/documentation/gentle-reminders/)、[更新器偏好](https://sparkle-project.org/documentation/api-reference/Classes/SPUUpdater.html)、[配置选项](https://sparkle-project.github.io/documentation/customization/)

## 本项目接入条件

- `scripts/build-app.sh` 当前生成版本 0.1.42、构建号 43，使用 ad-hoc 签名；README 明确未经过 Apple 公证。Sparkle 的 EdDSA 更新包签名用于验证更新来源，不等于 Developer ID 签名和 Apple 公证，也不会解决首次安装的系统信任提示。官方建议条件允许时采用 Developer ID 与公证；没有 Developer ID 不应直接等同于完全无法使用 Sparkle，但当前分发条件下必须实际验证安装和重启。[Sparkle 签名与分发要求](https://sparkle-project.org/documentation/)
- 公钥随应用分发；私钥需妥善备份，在 CI 需要时通过受保护 Secret 使用，不能提交到仓库。当前 SHA256SUMS 不能替代内置可信公钥验证的更新签名。
- 当前使用 Swift Package 与手工拼装 `.app`，接入时需显式处理 Sparkle.framework、辅助程序、动态加载路径、权限与签名；不能仅添加一个 Swift 依赖就视为打包完成。
- `.github/workflows/release.yml` 当前直接发布 DMG 和 SHA256，接入后要补齐签名、清单和完整发布检查。保留已发布包不覆盖的规则；构建号严格递增，展示版本与 tag 保持一致。
- `Sources/LingChongDao/App.swift` 的退出流程可能异步恢复保持唤醒并取消退出，更新安装必须尊重这一结果。任务和审批处理中优先允许稍后重启；按 `PRIVACY.md`，重启后不恢复原内存任务列表。
- 应用外已安装的连接插件/helper 有自己的版本和安装路径；更新 `.app` 不意味着这些副本已经更新。新版本启动后应复用现有检测逻辑提示需要更新的连接插件，并测试新旧组合兼容性。
- 更新请求会访问 GitHub，应在隐私说明中补充该联网行为，不携带任务文本、项目路径或会话数据。
- 现有不含更新器的版本仍需用户手动安装一次包含更新器的新版本；后续版本才能通过该链路升级。

实现阶段至少验证：旧版本到新版本成功安装并重启、最新/跳过/稍后状态、离线与下载中断、篡改签名拒绝安装、从 DMG 直接运行或安装目录不可写、系统版本不兼容、保持唤醒退出恢复失败、更新后的插件状态，以及用户偏好和本地数据保留。当前产品范围不包含自动下载安装。
