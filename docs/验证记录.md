# 0.1.0 验证记录

验证环境：当前 Apple Silicon Mac，macOS 原生 Swift / SwiftUI / AppKit，Command Line Tools。没有完整 Xcode 的 XCTest 框架，因此保留 XCTest 套件，同时提供无需 XCTest 的验证入口。

- 独立核心与连接验证：27 项通过。包含状态排序、来源/线程隔离、重复和延迟事件、过期权限、socket 权限与单实例、超时、断线、原子写备份、已有配置保留及符号链接拒绝。安装均使用隔离临时 home。
- 应用状态验证：13 项通过。包含预览与真实会话隔离、真实待办优先、旧事件不打断审批、来源期限不延长、批准/拒绝仅回传对应请求。
- 打包 helper 与真实应用进程：ping、普通活动、权限超时和来源已过期四项通过。
- 原生 UI：设置页绿色开关/滑块样式与参考一致；宽度调整为 110% 后数值和预览同步，恢复默认可用。虚拟 Codex 审批点击批准，helper 实际输出 allow；虚拟 Qoder 复杂审批仅显示拒绝和打开来源，点击拒绝后实际输出 deny。示例命令不会执行。
- 原生问题预览：完整内容按自然高度展开，中文草稿输入后 Escape 收起，再次展开仍保留；提交示例回答后任务回到运行态。
- 顶部定位：刘海屏窗口采用 statusBar 层级，解除普通窗口 frame 约束，hosting root 忽略安全区。诊断确认屏幕顶边与窗口顶边差值 0。

真实 Qoder / Codex 的 Hook 配置尚未由开发过程安装或信任；需通过应用内「连接的应用」完成来源接入和新任务验证。当前未实测第二块显示器、全屏应用/Spaces 的全部组合及实体触觉反馈。

原始结果和原生截图位于 `docs/evidence/`。

## ZCode 危险命令审批不到岛的根因确认

用户实测守护模式下 ZCode 弹「Dangerous command requires your approval」时岛上仍显示运行中。排查确认：合成探针经插件原始命令注入 PermissionRequest，岛正常识别为活审批（helper 阻塞等待），接收端完好；zcode.cjs 中守护模式安全规则的 ask 固定 `approvalMode: "user-once"`，而权限请求的 Hook 闸门为 `runHooks: x && approvalMode !== "user-once"`——ZCode 对一次性危险批准有意不派发 Hook，防止自动放行。此类确认只能回 ZCode 完成；其余 ask 路径（always-ask 等）正常到岛。连接卡片与 README 已限定此边界，证据链见 [ZCode接入调研](ZCode接入调研.md) 2026-10-25 补充二。

## ZCode 点击定位到项目工作区

（已回退）ZCode 3.16.3 外部深链经静态分析确认只有 workspace/open、支付、分享导入、OAuth 四条路由，无会话级入口。曾实现「cwd 为真实本地目录时点击打开项目工作区」，但 ZCode 对 workspace 深链每次都弹自家确认框，用户反馈体验差，当日回退：点击一律「打开应用」，验证用例改为断言 ZCode 任何情况都不产生深链。证据与回退原因见 [ZCode接入调研](ZCode接入调研.md) 2026-10-25 补充。

## Qoder 定时任务点击不再报错

定时任务等智能体会话不在 Qoder CN 桌面聊天列表内，`qoder-cn://chat/open` 会被来源以「无法打开该会话」拒绝。Hook 载荷经真实日志比对无判别字段，故以任务工作区 `Documents/Qoder/<日期>/<短十六进制 ID>` 的 cwd 形态收敛深链范围：命中即回退「打开应用」，不弹来源错误、不误标已读；普通聊天不受影响。验证：`./scripts/verify-navigation.sh` 54 项通过（新增任务工作区正反 11 例）。证据与边界见 [Qoder会话跳转调研](Qoder会话跳转调研.md) 2026-10-25 补充。

## 需要处理时自动展开

任务进入任何需要用户处理的状态——「待批准 / 待回答 / 本轮结束 / 已完成 / 失败 / 中断」——顶部岛都会自动下拉展示，不再依赖鼠标悬停；不抢键盘焦点，8 秒无操作后自动收起，鼠标停在岛上或正在输入/处理时延后收起。同一会话先后到达两个审批或问题时，各自重新下拉；运行中与已读状态不触发。设置项「屏幕顶部 → 需要处理时自动展开」默认开启（沿用原「任务完成后自动展开」的存储键）。隔离实例验证日志：`LINGCHONGDAO_COMPLETION_REVEAL expanded=true`，8 秒后 `LINGCHONGDAO_COMPLETION_COLLAPSE`；独立验证 39 项通过。2026-10-25 从「仅完成/失败」扩展为全部需要处理的状态：`Stop` 仍落为「本轮结束」不推断成功（核心契约不变），只是结束提示同样参与自动下拉；判定逻辑抽为 `IslandCore.AttentionRevealTracker`，`./scripts/verify-attention-reveal.sh` 以真实 HookNormalizer、SessionReducer 与 Tracker 验证 22 项通过。同日加聚焦下拉：自动下拉的展开面只渲染本次需要处理的会话（`AttentionRevealTracker.Announcement.attentionSessionIDs` → `IslandWindowContext.attentionFocus`），运行中任务不出现在该次下拉内容里；收起或用户自己点开、悬停展开后恢复完整列表。聚焦内容被处理完（批准、关闭提示、已读）自动收起，不留空面板。

## 插件卡片安装 / 更新合并与卸载确认

四个平台（Codex / ZCode / DeepSeek Harness / Qoder）的插件卡片改为：未安装才显示「安装插件」，随应用分发的插件版本或文件内容比已装副本新时才显示「更新插件」，正常接入时不显示安装入口；真正异常（来源不完整、被禁用、旧 Hook 未清理）仍显示「修复插件接入」。更新判定由 `PluginPackage` 比较清单版本（数字段）与包内文件摘要，宿主装得更新时不会回退。卸载改为卡片底部独立的灰色垃圾桶图标，点击后弹出二次确认，确认后才调用对应平台的卸载流程。连接测试新增版本排序与 ZCode 更新检测用例；独立验证 39 项通过。

## 「打开来源应用」冷启动修复

现象：点击卡片上的「打开 ZCode」后 Dock 图标一闪即消失，应用未出现窗口。排查发现当前终端/宿主环境带有 `ELECTRON_RUN_AS_NODE=1`，灵宠岛启动时继承了该变量并转发给被启动的 Electron 应用，导致 ZCode 以 Node 模式运行（直接运行其可执行文件会进入 Node REPL），启动协议后约 5 秒退出；系统日志显示 `dev.zcode.app` 启动后立即终止，应用自身无崩溃报告。修复：打开按钮改为用 `/usr/bin/open -a <应用>` 启动，并在子进程环境中剔除 `ELECTRON_RUN_AS_NODE`、`NODE_OPTIONS`、`NODE_ENV` 等变量；同时以干净环境重启灵宠岛。实测冷启动 ZCode 后可保持运行，失败时卡片下方会显示原因。

## Codex 更新插件无反应修复

现象：Codex 卡片显示「0.1.4 → 0.1.5」并出现「更新插件」，点击后状态不变。排查发现此前为统一展示名，直接修改了 `Application Support/LingChongDao/codex-plugin/marketplace` 内的插件清单，导致持久目录与 `owned-tree.sha256` 归属摘要不一致；`publishSource` 在复制新版本前按「更新中断且恢复资源不明确」中止，错误显示在列表底部，因此看起来没有反应。修复：`publishSource` 现在区分「目录本身仍符合灵宠岛插件契约、仅 marker 过期」与「目录不可识别」两种情况，前者允许备份后替换并写入新 marker；同时把安装/更新/卸载/导出的失败改为模态弹窗「操作未完成」，直接显示完整原因；卸载确认也统一到同一个弹窗状态机。已用 Codex CLI 将本机插件从 0.1.4 更新到 0.1.5 并确认启用。

## ZCode 点开历史任务不再重复弹岛

用户实测点开已结束且查看过的 ZCode 任务，岛上又弹新的「灵宠岛 / SessionStart · 运行中」。根因：ZCode 恢复历史会话时也派发 `SessionStart`（`source: "resume"`），岛此前把该事件无差别置为 running。修复：`HookNormalizer` 把 `source=resume` 归一为新事件 `.sessionResumed`，`SessionReducer` 对其只刷新 cwd/标题元数据、不改相位不置未读；真实工作（UserPromptSubmit、工具事件）照常上岛。验证：`./scripts/verify.sh` 40 项通过（新增 resume 正反用例），17 个专项验证脚本全部通过，`swift build` 全目标通过；XCTest 套件补 `testResumedSessionStartDoesNotResurrectEndedTask`。证据链见 [ZCode接入调研](ZCode接入调研.md) 2026-10-25 补充三。

## prompt 标题取数按来源拆分

ZCode 内置浏览器打开时会自动把 `<in-app-browser-context source="ambient-ui-state">` 块注入 prompt 头部，卡片标题被 XML 标签抢占（Codex 无此注入，观感「取的不一样」）。按「各来源互不影响」要求把 prompt→标题重构为按来源的独立策略 `PromptTitlePolicy`：ZCode 剥离开头成对的 ambient 块（未闭合不剥）、Codex 保留附件包装规则、其余来源原样规整，新增来源默认 plain 档。用例断言同一段 ambient prompt 在 ZCode 下取真实提问、在 Qoder 下保持原样，规则互不渗透。`./scripts/verify.sh` 41 项、17 个专项脚本、全目标编译通过。证据见 [ZCode接入调研](ZCode接入调研.md) 2026-10-25 补充四。

## 任务行滑动清除（含运行中卡死任务）

展开岛的任务行新增左右滑动清除手势，对齐 iOS 通知行与 macOS 通知中心：行跟手移动并随位移淡出，越过阈值（110pt）或快速甩动（预测位移超 420pt）后飞出、被岛体圆角裁切，其余行以表面弹簧收拢；不足则回弹。过阈值触发一次 Force Touch 触觉反馈（跟随系统触觉设置）；最后一行滑走后岛自动收起；VoiceOver 提供命名操作「移除任务」。语义上滑动=手动清除：`SessionReducer.dismissSession` 增加 `force` 通道，运行中的任务允许手动滑走（解决来源额度用尽等"不再说话"的任务永远占用岛的问题），同一会话有新事件时照常重新出现；实时待批准与待回答请求无论 force 与否都不会被清掉，原"运行中不可普通清除"的既有约束不变。验证：`swift run lingchongdao-verify` 43 项通过（新增滑动强制清除、活动后重现、强制清除不吞活请求三项）；README 交互段落已更新。首版只挂 SwiftUI `DragGesture`，实测触控板双指轻扫（`scrollWheel` 事件）与按住拖动（被 `Button` 吞掉）都不生效，遂把整行输入收敛到 AppKit 捕获视图 `RowGestureCatcher`：鼠标按下/拖动/抬起与双指滚动统一驱动同一套跟手动效，小幅按压回退为点击打开会话，纵向滚动透传列表，注：macOS 26 SDK 的 `acceptsFirstMouse` 已改为 `NSEvent?` 参数。后续按 macOS 通知设计补齐工作台：手势组件抽为共享 `SwipeDismissRow`（`catchesMouse` 区分整行单目标与含按钮行——岛上接管鼠标拖动，工作台行内有「打开应用」等按钮，改用滚动捕获 + SwiftUI 拖动组合，不遮蔽子按钮），工作台任务卡片支持双指轻扫 / 按住拖动清除与悬停灰色 ×（`NotificationCloseButton`，点击原地淡出后移除，实时待批准与待回答不显示 ×）。× 初版挂在行左上角、悬在图标上方，与 macOS 不符；按实测截图改为 macOS 布局：行首预留 27pt 槽位（图标整体右移、布局稳定），× 骑在行左上角——上缘探出卡片顶边约一半（offset y -4），第二行骑在分隔线上，与 macOS 通知一致；悬停淡入，指针在探出部分与行之间移动时用 closeHover 合并状态避免闪烁；飞出行不再做卡片级 clipShape 以免裁掉探出的 ×。自验：`LINGCHONGDAO_VERIFY_CLOSE_BUTTON=1` 强制显示 × 后用 `screencapture -l<窗口ID>` 截取工作台实窗，与 macOS 参考图逐项比对通过，证据见 `docs/evidence/close-button-placement.png`。，列表以卡片圆角裁切飞出动画并用表面弹簧收拢。调研依据：macOS 通知悬停左上角灰色 ×、双指轻扫甩走、无常驻关闭按钮（Apple 支持文档与实测习惯）。注：本机 CLT 自 10-25 下午起缺失 `libSwiftUIMacros` 宏插件与 XCTest 框架，构建以 `SDKROOT=MacOSX26.5.sdk` 临时绕过，`swift test` 待重装 CLT 后恢复；XCTest 套件已补 `testSwipeForceDismissClearsStuckRunningSessionAndResurfacesOnActivity` 与 `testForceDismissNeverSwallowsLiveApprovalOrQuestion`。
