# 连接页切换卡顿

2026-10-26：连接卡片操作区外层 ViewThatFits 同时提供横向与纵向候选，内部 connectionActions 又嵌套另一层 ViewThatFits。每个候选重复构造按钮，SwiftUI 在布局与偏好收集期间反复测量。原生采样显示主线程主要位于 SwiftUI / AttributeGraph 的布局测量，而非应用检测。

用真实 ConnectionsView 在 NSHostingView 中创建并布局 600/850pt 内容区，检测刷新约 38ms，首次显示 544ms，重复显示 315–326ms（未优化测试程序）。只删除内部嵌套，保留外层宽窄两种布局，首次 121ms，重复 62–67ms。同一程序与数据，均未修改连接检测逻辑或图标缓存。

回归命令：`bash scripts/verify-connection-layout.sh`。每次验证四次创建/布局，任何一次超过250ms判定失败，整套连续运行三次。检测会读取本机应用状态，不修改连接配置；活动日期仅在测试进程内存设置。依赖本机性能与应用环境，极端负载下需要结合采样判断。

辅助功能自动点击因权限不可用，使用直接驱动同一原生视图的性能检查代替，未宣称实际点击自动化通过。


## 完整工作台导航复查

同日用户仍反馈卡顿。上一轮仅测孤立 ConnectionsView 创建，250ms 阈值也过宽，不能代表工作台内的导航。补充测试后，在包含侧边栏、父级 ScrollView、真实按钮点击、页面生命周期、宠物订阅和刷新逻辑的完整 WorkbenchView 中复现：首次停顿396ms，重复330–349ms。

单变量对照：移除整页转场没有改善（350–470ms）；仅关闭进入页刷新也没有改善（344–374ms）。保留原有转场与刷新，仅用单份 HStack 替换剩余 ViewThatFits，降至首次80ms、重复39–42ms。采样集中在 NSHostingView.layout / AttributeGraph / SizeFittingLayoutComputer，说明父布局对不同宽度提案的反复测量仍会放大候选视图成本。

最终使用 ConnectionActionsLayout：只创建一份按钮，缓存理想尺寸，按可用宽度自动换行，详情/删除区域维持右对齐。保留原转场、即时刷新和全部操作。完整测试三轮通过，1000pt首次约46–49ms、重复约30–34ms；850pt重复约28–39ms，阈值收紧为100ms。均为本机原生测试进程的主线程响应间隔，不等同于屏幕逐帧显示延迟。

回归命令：`bash scripts/verify-workbench-navigation.sh`。在测试进程内部向窗口发送鼠标事件，真正触发侧边栏与检查连接按钮；截图检查选中指示，防止点击未生效却通过耗时断言。三轮覆盖1000/850pt窗口和任务、设置、连接页往返，采样点击后1.5秒内的主线程最长停顿。读取已安装应用资源和连接配置，不启动桥接、不安装插件。设置使用隔离域。

证据位于 `docs/evidence/navigation-performance/`，包括完整窗口截图和修复前后耗时。旧的孤立布局测试保留为辅助检查，导航测试才覆盖此次报告的路径。
