## 前次问题基线

### 1. 动效验证脚本编译失败（P1，新增）

证据：`scripts/verify-motion.sh:33` 起手动列出编译源文件，编译 `IslandView.swift` 时遗漏其依赖 `Sources/LingChongDao/Views/SwipeDismissRow.swift`。运行 README 的 `./scripts/verify-motion.sh`，退出码 1，报错位置 `IslandView.swift:304`：`cannot find 'SwipeDismissRow' in scope`。

影响：贡献者按 README 执行验收会失败，动效回归没有真正执行。本轮未据此判定 App 动效本身有问题；完整 App 的 Release 编译成功。应补齐测试编译依赖并重新执行该专项。

### 2. 审批示例和开发契约仍落后于实现（P2，复现）

README 中的开发演示声称发送 `examples/approval.json` 后出现可交互的 Codex 审批。该示例缺少当前回合与审查者元数据；`AppModel.swift:165` 会检查 `CodexApprovalContext.reviewer`，无法确认人工审查就回来源。

本轮向临时隔离 App 实际发送该示例：返回 `{}`，诊断为“审批由 Codex 处理，灵宠岛不代替来源作决定”，发送前后均为 0 个活动或未读会话。示例不执行其中的 `pwd`，也没有出现审批卡片。可引导用户使用现有“任务总览 → 交互预览”，或提供独立验证夹具，保持现有生产审批判断。

`docs/CORE-CONTRACT.md:7` 的来源枚举、`:34` 关于 Qoder 可 allow/deny 的说明也已过期；实际 Qoder 插件只观察状态。应同步当前契约或显著标为历史记录。

### 3. 首次安装入口与完整前置条件（DMG 入口和工具要求已补齐）

原 README 首段“运行”直接要求从 `/Applications/灵宠岛.app` 启动，未清楚区分下载 App 和构建源码。现已在顶部补充 DMG 下载、拖入 Applications 和来源连接三步，以及 macOS 14+、Apple Silicon 范围；开发章节单独列明 Swift 6 和 Python 3 要求。

`Package.swift:1` 要求 Swift tools 6.0；`scripts/build-codex-plugin.sh:22` 强制验证 arm64，`:23–30` 要求 Python 3。这是默认 App 打包的必经步骤。Intel 本机编译的 x86_64 helper 会在这里失败，不能将“macOS 14+”理解成 Intel 打包已支持。

预编译 App 用户不需要另装 Swift、Python 或 Node。当前 Apple Silicon 打包范围已明确；Intel 兼容性不在本次承诺内。

### 4. DMG 分发链路（本地交付已补齐，线上发布待推送仓库）

已参照 [ClearZip v1.0.0](https://github.com/LJjayyy/ClearZip/releases/tag/v1.0.0) 增加 `scripts/package-dmg.sh`，生成版本化 DMG 与 `SHA256SUMS.txt`。镜像提供 `灵宠岛.app`、指向 `/Applications` 的拖放入口、安装说明和许可文件；已只读挂载，并在临时目录模拟复制安装，签名、老板鼠资源、五个插件及 helper 检查均通过。

实际 App `codesign --verify --deep --strict` 通过，签名类型为 ad hoc、无 TeamIdentifier；`spctl --assess --type execute` 返回 `rejected`（退出码 3）。沿用维护者 ClearZip 的签名策略，README、镜像和 Release 说明均提供首次打开的 Apple 官方指引。Developer ID 和公证属于后续体验改进，不再作为本项目开源或 DMG 分发的前置要求；其他 Mac 的互联网下载与首次打开仍未实测。

### 7. 两个验证脚本没有执行权限（P3，新增）

`scripts/verify-connection-layout.sh` 和 `scripts/verify-workbench-navigation.sh` 当前为 0644。直接 `./scripts/verify-connection-layout.sh` 返回 permission denied（126）。显式用 Bash 执行时两项均通过，因此属于命令入口问题。需要赋予可执行位，或将相应文档调用方式统一为 `bash ...`。

Qoder / ZCode 的转发脚本虽也为 0644，但 Hook 命令显式经 `/bin/sh` 执行，未将其列为同类问题。

### 8. 未安装 Codex 时显示“修复插件接入”（P3，新增）

在没有来源 CLI / 配置的隔离环境，Codex 卡片显示“配置需要检查”和“修复插件接入”。`CodexPluginService.swift:55` 将找不到 CLI 作为异常，`:80` 映射为配置错误。

新用户尚未安装来源时会误以为已有配置坏了；可区分“未检测到来源 / 请先安装”和“已有安装需要修复”。本轮界面状态来自隔离环境，未用于推断维护者真实 Codex 安装损坏。

### 9. 老板鼠的第三方角色权利资料仍未闭环（待核验，按维护者决定公开保留）

`assets/default-pet/design.json:10` 明确记录 Jerry 角色参考，并要求保持其辨识度。现有仓库记录未提供相关角色再分发的授权证据。本轮依维护者要求公开保留老板鼠作为品牌；已在素材说明中如实记录来源、公开范围和代码 MIT 的边界，没有将公开收录描述为获得第三方授权。本项是证据缺口，不作侵权结论。

## 用户下载后的实际体验

### 普通用户通过 DMG 安装

1. 从 GitHub Releases 下载 `LingChongDao-版本-macOS-arm64.dmg`，打开并将“灵宠岛”拖入 Applications。
2. 从“应用程序”启动，看到老板鼠工作台和顶部岛；不需要安装 Swift、Python、Node 或构建源码。首次打开的系统提示处理方式与 ClearZip 一致。
3. 在“连接的应用”安装所需插件，按来源要求审查、启用并重启，再开启新会话。之后在原来的 AI 工具里工作，灵宠岛显示任务状态与提醒。
4. 关闭工作台后顶部岛继续运行；退出与再次打开通过菜单栏或“应用程序”完成。更新前退出旧版，再拖入新版替换。目前需手动启动与更新。

### 开发者获取源码时

1. 用户进入 GitHub，通过 Code 下载 ZIP 或 clone，得到源码；目前仓库内容本身没有可直接双击的 App。
2. 在 Apple Silicon、macOS 14+ 上准备 Swift 6 工具链和 Python 3，解压后进入项目根目录。
3. 运行 `./scripts/build-app.sh release`，得到 `dist/build.noindex/灵宠岛.app`。首次需要编译，但 Swift 主包没有第三方包依赖。再运行 `./scripts/install-local.sh --no-build` 安装到 `/Applications/灵宠岛.app`；更新前要先退出当前版本。
4. 启动后看到暖纸色工作台和老板鼠，菜单栏与屏幕顶部同时驻留。没有来源任务时列表为空，提供“连接应用”入口；老板鼠能点击互动。关闭工作台后仍在顶部运行，可从菜单栏重新打开。
5. 用户先安装并使用自己的 Codex、Qoder CN、Claude Code 等来源应用，再在“连接的应用”安装对应插件或 Hook。无需在灵宠岛填写自己的模型 API Key；实际 AI 会话仍由来源应用提供。
6. 根据卡片提示在来源审查/启用插件，重启来源并开启新会话。已安装不代表已信任，也不代表旧会话加载成功；收到新活动后才算接通。灵宠岛不会扫描旧聊天补齐任务列表。
7. 日常继续在原应用工作，顶部显示运行、等待与结束提示。Qoder CN / Codex 可在受支持的本机会话中定位会话；部分来源只打开项目或应用。问题通常回来源回答，岛内批准仅适用于当前支持且可核验的权限请求，具体以卡片能力为准。
8. 退出灵宠岛后，来源工具按自身流程继续处理；插件不会自动启动灵宠岛。重启电脑和升级 App 目前都需要用户自行操作。

DMG 已在本地构建并验证，尚未上传 GitHub。本轮没有在另一台 Mac 上完整模拟互联网下载和首次启动。
